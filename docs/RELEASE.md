# Changelog and releases

This page is for maintainers preparing a release, and for anyone who needs to correct what the
changelog says. Contributors only need a conventional PR title and, where it applies, a
`Representation-Change:` line; both are described in `CONTRIBUTING.md`.

## How the changelog is built

`CHANGELOG.md` is generated by [release-plz](https://release-plz.dev/) from the
conventional-commit history when a release PR is opened. PRs are squash-merged, so each PR title
becomes one commit subject and one changelog bullet.

- **Do not hand-edit `CHANGELOG.md` in a feature PR.** Two PRs that both add bullets under
  `## [Unreleased]` conflict on the same lines.
- **Do not hand-write a note into an open release PR either.** release-plz regenerates the
  pending section on every run, so the note is lost the next time the PR updates. A
  `Representation-Change:` trailer is the way to get a note into the changelog.
- `feat` and `fix` get their own changelog groups; the other types fall under **Other**.
- A commit whose trailer declines (`Representation-Change: none`) is grouped by its
  conventional type, so a declining `fix:` is listed under **Fixed**.
- A commit whose trailer declares a move is listed under **Representation changes**, at the
  top of the release.

## Attaching the disclosure text

The generated bullet is the commit subject only. For every commit filed under
**Representation changes**, `scripts/inject_representation_disclosure.py` reads the trailer
from the raw commit message and quotes it under that commit's bullet. A declining commit is
never filed there, so the script never quotes one.

Run the script on the release PR, and again after any push that regenerates the pending
section. It is idempotent. CI runs its `--check` form in the `Changelog grouping audit` job, so
the release PR stays red until the script has run.

```bash
python scripts/inject_representation_disclosure.py          # attach; idempotent
python scripts/inject_representation_disclosure.py --check   # what CI asks
```

## Checking the grouping

`scripts/check_changelog_grouping.py` renders the changelog through real git-cliff over
`<latest tag>..HEAD`. It checks that nothing under **Representation changes** opens with a
decline word and that nothing declaring a move is filed elsewhere. It needs `git-cliff` on your
`PATH`:

```bash
python scripts/check_changelog_grouping.py
```

The decline words are defined in `scripts/check_representation_change.py` (`NONE_VALUES`) and
repeated in `release-plz.toml` and in `DECLINE_WORDS` in `scripts/check_changelog_grouping.py`.
The watched directories (`WATCHED_PREFIXES`) are repeated in `release-plz.toml`. The tests in
`tests/python/test_representation_change_trailer.py` and `tests/python/test_changelog_grouping.py`
check that these copies agree, so change them together.

## Correcting a released changelog

**Add a retrospective note to a released section.** A release only prepends to
`CHANGELOG.md`, and the GitHub release body is never revisited once its tag exists. So a
representation summary for a cycle that shipped without trailers can be added afterwards:
edit the released section and run `gh release edit <tag>`. This does not replace declaring
changes as you make them, because whether an input was previously rejected or accepted cannot
be reconstructed later.

**Correct a merged disclosure through the script, never by hand.** A merged trailer cannot
be changed, and a hand edit to `CHANGELOG.md` is regenerated away and fails `--check`. Register
the correction in `EDITORIAL_CORRECTIONS` in `scripts/inject_representation_disclosure.py` and
re-run the script; the table's docstring says what a correction may contain. In a released
section, delete the stale block first so the re-run can write it back.
